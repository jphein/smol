## 0. The one thing that will confuse you first

**`rust/clock/version.txt` says `345`. The fleet is running `906`/`907`.** Both are true.

- **345** is the last *numbered release* (v345 "Riveted Furnace", commit `315b5c8`).
- **906/907** are **canary `SMOL_BUILD_NUMBER` dev pins** — bench builds stamped high so they out-rank
  the fleet's monotonic OTA gate (#128 tracks the pollution). **There is no release v906.**
- So **the whole Bard campaign is live on the fleet and is not in any numbered release.** The v346 train
  (PR #266) is where it lands.

Sigil names are derivable and self-checking: `noun = FORGE.nouns[n % 20]`,
`adj = FORGE.adjectives[(n / 20) % 20]`. A build number and a sigil word that don't satisfy that are a
**bug in the document** — that is how "build 905 Riveted Furnace" was caught (905 → *Flux* Furnace).

### 1a. ⚠️ The one claim that is a code-reading, not a measurement
`443ea34` *"keep the active screen alive through a WiFi burst"* is described as substantially fixing
JP's *"UI freezes for wifi and stuff."* **That is read off the code, not timed.** It also **corrected the
diagnosis**: in steady state nothing paints a clock — the screen is frozen on the last app frame **by
deliberate policy** (#153: *"a routine burst → draw NOTHING; a still clock beats a spinner"*), and the
clock-instead-of-your-screen behaviour is **boot-only**. So the freeze is a *policy* that only began
reading as a crash once the Bard was on the glass: **a frozen typewriter looks wedged.**

`07aa3a7` + `a15a91c` add the instrumentation to turn that into a number. **When the first freeze
measurement lands, replace the code-reading in three places** — README's Bard row, the Embassy doc's
benefit-1 row, and this file.

## 6. Live-state gotchas — you will trip on these in the first ten minutes

1. **No board is on USB. DIAG/MQTT is the only observability channel.** No serial, no `espflash monitor`.
   Plan any investigation around retained topics + the HA REST API.
2. **The crown moves.** id8 → id50 → id5 within one hour today. **Anything keyed to a specific crown id is
   fragile.** Read the current owner from `smol/mesh/channel` = `MC|owner|channel|seq`. The #155
   `channel_hint` retained topic is the operator lever if you need to *choose* the crown.
3. **`sensor.smol_<id>_peers`'s STATE is only the role** (`gateway`/`leaf`). **The roster is in its
   `peers` ATTRIBUTE.** Reading the state and concluding "no peers" is how the fleet got reported as one
   board — twice, in one hour.
4. **id7/id9 entity families are live but dead.** `sensor.smol_7_*`, `smol_9_*`,
   `update.smol_7_dominion` all answer queries for ids nothing has broadcast in months. **A per-node
   entity existing is not a node existing** — and the inverse bites too: **frozen values are not evidence
   a board is dead.** Cleanup is team-lead's.
5. **Two unidentified ids, possibly watches.** **id122** (= *Celestial Crown* by the naming formula — note
   the collision with smol's word for the elected gateway) and **id42**. The watch treats
   `node_id == 42` as a **sentinel meaning "derive the id from the MAC"**, so a field watch reports
   whatever its MAC derives to. **Unresolved; settle by matching roster MACs.** It matters beyond
   bookkeeping: **an unaccounted mesh peer is a variable in every mesh measurement from now on**,
   including Phase 2's harness if it is re-run.
6. **Liveness: prefer the shortest-chain signal.** Absent telemetry crosses board → ESP-NOW → crown →
   WiFi → broker → HA, so it only means *"something in a long chain is broken"* — and retained MQTT has
   faked liveness here repeatedly. **Absence from the crown's ESP-NOW peer list** needs no router, DHCP or
   broker, so it genuinely means *not running*. **When two signals disagree, trust the one with fewer
   hops.**
7. 🔴 **`tools/ota_verify.sh` was broken until `da1cba8` — and a broken diagnostic does not error.**
   **Four** defects (`da1cba8`, `fa2e6aa`), and two inverted its core proof: PASS tested `slot="ota_1"`
   when the firmware publishes a **numeric** slot and an OTA reboot reports `rst=sw`, so **every genuine
   OTA was reported as "USB flash, NOT an OTA"**; and DEATH-POINT fired on **retained ghosts** (a retained
   value never changes, so it satisfies "frozen for 30 s+" for free). The off-channel check compared
   **free heap** to the mesh channel via an unanchored `ap=[0-9]+` matching the tail of `heap=42040` — and
   note **`ap=` does exist** (`ap=<ch>:<rssi>:<bssid>`, conditional), which is *why* the bug survived: a
   sometimes-absent field gave it an alibi on leaves. **Anything an older copy of that harness told you is
   suspect.** Firmware now also publishes **`apch=`** — coexist's *believed* channel vs `ap=`'s *observed*
   association, deliberately not redundant. **The design principle it validates is
   luna's, and it is the day's other keeper: a self-reported manifest beats a hand-maintained list** —
   the same reasoning that made registry discovery right (§2).
8. **After ANY OTA, a USB flash silently lands in the slot that will not run.** `espflash erase-region
   0xf000 0x2000` (otadata only — spares NVS, so the node id survives) first, then reset, then flash, then
   **read the `Loaded app from offset` line.** It reads as a brick and is neither. Cost an hour today.
   Also: **espflash v3** for `main` images (v4 refuses esp-hal 1.0.0-rc.0) — **untested for the branch's
   esp-hal 1.1**, which you would discover mid-recovery.
