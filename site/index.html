ESP32-C3 · 72×40 OLED · no_std Rust

One binary. Many apps. Many chips.

smol is a platform for very small computers. One no_std Rust binary carries a whole registry of apps — a clock, a mesh-wide multiplayer snake, a roster radar, a living creature, and a 260K-parameter transformer that writes children’s stories with no WiFi and no cloud — and you move between them with the one button the board has. Underneath, the fleet services come free with the platform: boards find each other over ESP-NOW with no router in the middle, elect a gateway, publish themselves into Home Assistant, take every setting back from it without a reflash, and update themselves with signed firmware over the air — even the WiFi-less ones, over the mesh. It started on a $3 chip. Today it is five targets across four chip families — RISC-V and Xtensa, a 72×40 monochrome OLED and a 2.8″ colour touchscreen, all speaking one wire format to each other.

01 — The platform

One binary carries all of it.

smol is not an app with some features bolted on; it is a small platform, and everything else on this page is something running on it. Across the whole fleet there is one firmware source, and for any given board one image — the chip and the tier are chosen together, per build. Inside it, every screen is a plugin — its own state struct implementing one trait — and a single table wires them into the menu you reach with the board’s one button. There is no allocator, no Box<dyn>, no vtable, and no dynamic loading: the whole registry is resolved when the binary is built, so a plugin costs you flash and nothing else. Which plugins are present is a build tier, not a runtime setting — and the tiers stack, so the cheapest board and the fleet gateway run the same code paths with a different slice compiled in.

◇
Static dispatch
Enum-delegation: one centralized match hands each hook to the live plugin. Every call inlines — no vtables, no function pointers.
◇
A union, not a sum
Only one screen is ever live, so the active plugin’s state is a tagged union sized to the largest variant — less RAM than keeping every app’s state side by side.
◇
The menu builds itself
A &'static [AppDesc] table is the registry. Add a variant, a module and a row — the BOOT-button menu picks it up.
◇
Hardware is borrowed
One display, one radio, one sensor block, handed to a plugin per call. A plugin never owns the hardware, so two apps can never fight over it.
◇
Tiers, not toggles
default is the clock and the games with no radio at all; wifi adds the network and the whole OTA stack; espnow adds the mesh. Each tier contains the one below it.
◇
A very small core
Boot, an always-on mesh background block, and a dispatch core of about a dozen lines. Everything a person actually looks at is a plugin.
02 — The targets

One fleet, many kinds of silicon.

smol began as one binary on one $3 chip. The roster is now five targets across four chip families, and the folder targets/ is the roster — one directory per board, each carrying a manifest that declares its chip, its firmware flavour and whether it produces a download. Adding a folder adds a target; there is no second list anywhere. Badges are honest, and the distinctions behind them are the ones that have cost us time: 🟢 glass-verified — a human watched it work · 🟡 mesh-proven — heard on the mesh, but the fleet firmware only compiles for it, which is a real claim and a much weaker one than builds.

04 — The Bard

The board writes you a story.

The Bard is the app that proves the platform: it is a plugin like any other, it shows up in the same one-button menu as the clock, and it is the reason the rest of this page is not a toy claim. Press the button and a real transformer starts composing — 260,000 parameters, int8, from the same llama2.c/TinyStories lineage the big toy models come from — on a chip with 400 KB of RAM and no floating-point unit. The weights never load: the model is executed in place from flash, memory-mapped, so all 283 KB of it costs zero bytes of RAM. There is no WiFi, no cloud and no gateway in the loop — a board alone in a drawer can tell a tale. Every node gets its own protagonist, so id8 tells owl stories and its neighbour tells dragon ones.

72×40 · SSD1306✒ composing

Typing at the board's real reveal rate — 160 ms per character, the firmware's own default. About five lines of fourteen characters fit at once, so the screen is a window the story moves past — not a container for the story. This excerpt loops; the board itself never stops.

Verified, not asserted

It really is a transformer, and we can prove it.

The interesting risk in a port like this is not that it crashes — it's that it runs beautifully and produces subtly wrong arithmetic. So the forward pass was pinned against two independent implementations: an int8-exact reference mirroring the accumulation order, and a from-scratch fp32 one written during review. It agrees token-for-token, 146 of 146 ids, full text. The obvious reference — upstream runq.c — was disqualified: it silently drops in-dimension elements 128..171 of every w2 row when the row length isn't a multiple of the group size. The golden gate is therefore cross-implementation, not cross-port.

🟢 On glass — a 67-token story on the bench board, then a canary soak that survived a hard power-cycle from the inactive OTA slot. Set Bard:0 from Home Assistant and a node boots straight into composing. And it no longer ends. A sliding-window rewrite (#302) removed the terminal state, so a tale runs indefinitely — verified on glass: the pace was changed from 160 to 120 ms/char mid-narration from Home Assistant, without a restart, and the stack high-water came back byte-identical at 55,440 B across five consecutive reports spanning many tale boundaries. A window that reused memory imperfectly would creep; this does not move at all. Honest edges: generation in endless mode runs 224–274 ms/token (max 281) — 10–35% slower than a bounded story, because attention now always spans the full window, and the spread tracks whether the radio is bursting, not the model. Verified on the bench and canary (id8); the fleet-wide roll rides the next release train. Endless mode is near-continuous compute, so it is the fleet's worst-case power draw — no battery-life claim is implied. · #300 ↗ · PR #301 ↗ · #302 ↗

07 — The config surface

Every knob, without a reflash.

A platform you have to re-flash to adjust is not much of a platform. smol boards take their settings over the air, from Home Assistant, on a keyed config channel (#56) — one retained MQTT message per knob, relayed on to the boards that have no WiFi of their own. Parsing is strict and panic-free by design: a malformed or unknown value is ignored and the board keeps what it had, because the failure mode of a config channel must never be a brick. Identity is the deliberate exception — a node’s id lives in NVS and OTA never touches it, which is exactly what lets one image serve the whole fleet.

08 — Fleet services

What you get for free by joining.

The interesting part of a platform is rarely the API; it is what a program gets simply by being on it. A board that joins the smol mesh inherits a set of services it never has to implement: it is discovered, named, timed, watched, and updated. None of that is app code. All of it is the reason an app on a $1 board can be three hundred lines long.

🔒
Signed OTA, over the mesh
Firmware is ed25519-signed and hash-verified into an A/B slot. A board with no WiFi at all is updated through the mesh by the gateway (#40), one canary board at a time — never broadcast to the fleet.
♛
Gateway election
Boards elect the best-connected node as gateway and re-elect when it stops answering. The fleet is never left without one, even when the only candidate is a poor one.
⏱
Mesh time
The newest authoritative NTP sync wins and propagates. A board that has never seen the internet still knows what time it is.
📡
Discovery
Each node publishes its own Home Assistant discovery config, so it arrives as native entities with no YAML written by hand.
⚖
Observability
A retained per-node health record — boot slot, reset reason, heap floor, link quality, update outcome — so a silent rollback is visible instead of mysterious.
★
Identity
Every board is given a name from a fixed corpus, derived the same way on every node, so logs and dashboards agree on what to call it.
09 — Get the firmware

Put it on a bare board.

Prebuilt images are on the releases page — today the C3 mesh tier as a merged 4 MiB image, with a SHA256SUMS beside it. You need a board, a USB cable and espflash. Per-target downloads are landing now: the build walks the targets/*/target.toml manifests and packages every board that declares one, through the same reproducible-build path the over-the-air publisher uses — and each image ships a NOTES.md beside it carrying that chip's stack-floor provenance in plain words. The mechanism is merged; the release job that runs it is the next step, so treat per-target downloads as a capability rather than a published fact until they appear on that page. The full story — nightlies versus versioned releases, the reproducible-build ceremony, and the flashing traps — is in docs/RELEASES.md.

Read this first: published binaries carry placeholder credentials — including the mesh key. They are built from a clean checkout with throwaway values — good enough to compile, never good enough to ship — and the key is a fixed published placeholder on purpose, because a random per-build key would destroy the byte-reproducibility that makes an image's sha256 its identity. A board flashed from a download boots, drives the display and runs the menu, the games and the Bard. It will not join WiFi, reach a broker, or talk to an existing mesh.

🔑 So re-key before you trust your mesh. A key baked into a public binary is public: two boards flashed from the same download share a key anyone can extract. Placeholder-key boards can mesh only with other placeholder-key boards, and can never join a re-keyed fleet. To own yours, regenerate GROUP_KEY in rust/clock/src/secrets.rs — 32 random bytes, starting from secrets.rs.example — then rebuild and reflash. It is a rebuild, not a setting: the key is compile-time, and nothing on the dashboard can change it.

sha256sum -c SHA256SUMS
espflash erase-region --port /dev/ttyACM0 0xf000 0x2000
espflash write-bin --port /dev/ttyACM0 0x0 <image>.bin

The middle line clears otadata and is not optional on a board that has ever taken an update over the air: the board is running from the other slot, so a plain flash succeeds and then silently never runs. It spares nvs, so a provisioned node id survives. Afterwards, read the Loaded app from offset line — it names the slot that actually ran.

Boards already on the mesh do not update this way. They take ed25519-signed firmware over the air, one canary board at a time. Downloads here are for a board that does not have smol on it yet.

10 — Mission Control

How smol got built.

◇ The build ledger — 54 tasks and 35 agents, archived as of 2026-07-07. A record, not a live feed: the panels below show that snapshot, and each prints its own date.

This fleet updates itself. A team of agents built smol in the open — flashing firmware, wrangling git, and closing every wave behind an adversarial review gate — and it is now genuinely remarkable for $1–$3 boards: a shared-world MMO snake with treasure-powers; an ESP-NOW mesh with newest-wins time sync, realm-sigil names, and ~20-node-capable peer handling; an MQTT-native Home Assistant link (live battery, state-of-charge and grid on every OLED); remote per-node config straight from the dashboard (LED, units, plugin visibility, reboot, custom screens — even the MQTT broker leg and the OTA image host, and the physical pins: wire a button or lamp to a free GPIO and drive it from HA); per-node observability with config-drift detection and a live OLED mirror in HA; and — the headline — signed over-the-air updates that reach even the WiFi-less nodes over the mesh, plus The Mesh Familiar: one creature that lives on a board and hops to a neighbour when you unplug it. And tonight the fleet learned to heal its own updates: the WiFi-fetch deaf-window that stalled mesh-OTA was pinned at the packet level and answered two ways — proactive re-association (#217) and peer-sourced OTA (#237), where an updated board serves the next over the mesh so a single download seeds the whole fleet. And then the fleet learned to write: The Bard puts a real 260K-parameter transformer on the $3 chip, executed in place from flash, composing a fresh children’s story onto the 72×40 OLED at 202 ms per token — verified bit-for-bit against an independent reference before it was believed. And then it stopped being one chip: the roster is five targets across four chip families — RISC-V and Xtensa, monochrome and colour touch — with the ESP32-C6 watch in-tree as a subtree, an ESP32-C5 heard on the mesh, and an ESP32-S3 touchscreen glass-verified in August 2026 running both firmware flavours. Underneath it all, the async re-platform's first phase has merged. Hardware-verified on the fleet.

A packet capture caught it: the node completes its TCP handshake and sends the request, then goes bulk-receive-deaf within ~1 ms of its own transmit — it never acknowledges a single response byte while the server retransmits into the void. It reproduces identically on the new esp-radio 0.18 stack, so the radio rewrite is not the cure. Two fixes now attack it from both sides — proactive re-association off a weak AP, and never fetching on a follower at all (below). CHARACTERISED + MITIGATED. Issues #217/#237/#204.
  • PEER-SOURCED OTAThe gateway used to WiFi-fetch every image and relay it — re-opening the deaf window once per board. Now an already-updated node serves the image to the next over ESP-NOW, a crown baton handing the role along, so the WiFi fetch happens once per image and the rest of the fleet is sourced peer-to-peer on the mesh. Canary-one-at-a-time and ed25519-verify-before-flash are unchanged, and a failed peer-roll falls back to the old gateway relay — no new brick risk. SHIPPED in v345 (slice-1). Issue #237.
  • TAMPER-EVIDENT MESH LEDGER (L1–L4)An append-only, tamper-evident provenance log for the fleet, built as four host-tested layers: a per-node hash-chain (L1), a Certificate-Transparency-style Merkle anchor with inclusion proofs (L2), an ed25519 Signed-Tree-Head (L3), and a delta-state CRDT for conflict-free merge across nodes (L4). Each layer verifies what it signs; keys are provisioned on-device only. Cores landed and fully host-tested — firmware wiring is on the next release train. Issues #182/#183/#184/#185.
  • GO-LATEST — esp-hal 1.1 · esp-radio 0.18 · edition 2024A matched-set upgrade to the current Rust-on-ESP stack: the whole firmware moved to esp-hal 1.1, the new esp-radio 0.18 and the 2024 edition. In flight, canaried on a bench board within port scope — and it confirmed the coexist deafness is a physics-and-duty-cycle reality, not an old-stack bug. Issue #233.
  • MANY SILICON — THE FIVE-TARGET ROSTERsmol's mesh is no longer C3-only. The ESP32-C6 smartwatch runs a full SMOLv1 stack on Embassy and now lives in this tree as a full-history subtree; an ESP32-C5 touch board became the first non-C3 silicon ever heard on the mesh (2026-08-24); and an ESP32-S3 touchscreen became the first Xtensa target, glass-verified on 2026-08-26 running both firmware flavours — display, touch, mesh, NTP, MQTT and Home Assistant. Porting to each one hardened the wire spec. SHIPPED, with named remainders: CI cannot compile Xtensa yet, and the S3 has not taken an over-the-air update. Issues #231, #347, #388, #398.
  • THE EMBASSY RE-PLATFORM — PHASE 1 MERGEDThe fleet tier now runs under the esp-rtos async executor beside the superloop, with embassy-time's driver underneath it and bounded async waits replacing sends that used to spin on a callback that might never come. The reason is measured, not aesthetic: the WiFi burst that left a gateway mesh-deaf for about 15 seconds is ~169 ms under the async transport. Phase 1 merged (PR #391). STEP T — giving the seven transport pairs one declared owner — is the blast-radius step and is argued in full before its code is written, in docs/embassy/T-SCOPE.md. In progress. Issue #335.
  • PRESENCE & PROXIMITYMarauder’s Watch shows where every node is by ESP-NOW roster RSSI (near/far), and a treasure-hunt warmer/colder game rides the same signal — SHIPPED (#58/#60). Native BLE-beacon presence was tried and refuted on hardware — the ESP32-C3’s blocking runtime wedges BLE+WiFi coexistence at PHY calibration, so smol stays BLE-free; the presence path is an ESPHome bluetooth_proxy → HA instead (#22).
  • COLOR TFTAdd an ST7789 and NES/GB emulation becomes possible.

14 — Influences

Standing on shoulders.

smol didn't appear from nowhere. Its ESP-NOW → MQTT → Home Assistant plumbing is commodity — a well-trodden pattern many have built. What's actually novel is the whole: a no_std Rust game-console mesh on $3 boards, a deliberate single-radio burst time-share, and a retained-payload → mesh-rebroadcast downlink to display-only leaves. Below are the projects that shaped it, grouped by the thread each runs in — credited honestly, with what smol borrows and where it diverges. A few handed over portable ideas; most gave lineage, identity and nerve rather than code.

◇ Mesh & routing
  • MESHTASTICThe mesh ethos smol admires — multi-hop, self-healing, friendly per-node names, an MQTT bridge to the world. smol's realm-sigil board names and its now-shipped routed multi-hop + self-healing gateway election (#13/#14) trace straight back here; different PHY — ESP-NOW on 2.4 GHz, not LoRa. ↗
  • PAINLESSMESHA self-organizing WiFi mesh where every node is both STA and AP. The road smol didn't take — it chose ESP-NOW for lower power, lower latency and tighter game timing. The honest counterfactual. ↗
  • ALTHEAAn OpenWrt-based decentralized, incentivized mesh ISP — self-organizing routed mesh, per-link WireGuard tunnels, Babel routing, IPv6, bandwidth settled by micropayments on its own L1 chain. smol borrows the self-organizing-mesh + per-link-encryption ethos (its lightweight analog is ESP-NOW LMK keys, #12) and the routed-multi-hop idea (Babel is prior art for #13, shipped 2026-07-14 as a Meshtastic-style managed flood; Babel feasibility is the >16-node upgrade); it leaves behind the blockchain settlement and full IPv6-over-mesh — node-ids are smol's lightweight addressing. The most different influence — an L3 incentivized ISP vs smol's L2 game mesh — architectural inspiration, not a template. ↗
  • ZHNETWORK · aZHOLTIKOVA routed, multi-hop ESP-NOW mesh library that bridges to MQTT + Home Assistant autodiscovery. Direct prior art for true mesh routing — and it proved ESP-NOW multi-hop on these exact C3 chips first. smol now ships routed multi-hop too (#13, landed 2026-07-14): a hop-limit + a seen-set, table-free, with the first routed frame proven on hardware — the pattern ZHNetwork pioneered, in no_std Rust. ↗
  • ESP-NOW → MQTT → HA · LATTICThe exact ESP-NOW → MQTT → Home Assistant gateway pattern smol independently arrived at — direct prior art for smol's relay bridge, credited plainly. ↗
◇ Local-first ESP ↔ HA
  • BATTERY-EMULATORESP32 firmware (LilyGo, C++) that emulates a BMS to bridge repurposed EV battery packs to home solar inverters over CAN bus, with its own web UI. The one influence smol is actually wired to — smol reads its battery telemetry over MQTT and mirrors it on the OLED, a live interop neighbor, not just an idea. It bridges CAN↔inverter on the mains side; smol is a battery-powered ESP-NOW mesh display/relay — different job, same MQTT-native, local-first, HA-first philosophy. ↗
  • TASMOTAOpen-source, MQTT-first, local-first alternative firmware for ESP smart-home devices — a rich cmnd/stat/tele topic scheme, runtime config over MQTT (no reflash), an on-device web UI, a rules engine, robust OTA, HA MQTT discovery. smol's closest genre-cousin: it borrows the runtime-config-over-MQTT / no-reflash ethos (exactly what the node manager does), the MQTT topic conventions, and the OTA + HA-discovery + local-first values (smol just firewalled off a cloud-phoning logger). Differs in form — Tasmota is C++/Arduino on always-on-WiFi mains devices with a web UI; smol is no_std Rust, burst/battery, single-radio, so the control surface relocates to HA. Prior art for local-MQTT-ESP→HA that smol independently lands in a game-console/mesh form. ↗
  • WLEDThe gold standard for Home Assistant polish — device-grouped typed entities, auto-discovery, its own ESP-NOW sync, a slick on-device web UI. smol borrows the entity-structure lesson; it can't host an on-device UI (the burst radio is deaf most of the time), so its node manager lives in HA instead. ↗
  • ESPHOMEThe YAML→firmware ecosystem and its always-connected native API. smol stays MQTT-native on purpose — the persistent native API fights the single-radio burst model, and no no_std-Rust ESPHome exists to build on anyway. ↗
  • ESP_WIFI_REPEATER · MARTIN-GERProof that an ESP is a real router — concurrent STA+AP, NAT, a console, MQTT, ACLs. Inspires smol's gateway-as-network-citizen role and shows concurrent multi-role radio is achievable. ↗
  • ESP3DESP8266/ESP32 firmware that bridges a 3D-printer or CNC serial port onto WiFi with a web UI — serial-over-WiFi, telnet, even Home Assistant notifications. smol borrows the ESP-as-WiFi-bridge-with-web-control appliance ethos: make a dumb serial device networked. Differs — ESP3D is one device ↔ one browser; smol is a multi-node mesh whose UI is the OLED + HA, not a per-node web page. ↗
  • ESP-LINK · JEELABSAn ESP8266 WiFi↔serial bridge that can remotely reflash an attached AVR/ARM MCU over WiFi (an stk500v1 programmer fed by HTTP hex upload), with a web console. smol borrows the gateway-bridge ethos and cites it as prior art for firmware-over-WiFi alongside OTA (#6). The honest distinction: esp-link flashes a separate attached chip — it's the programmer, not the target — while smol's OTA self-updates the ESP itself into an inactive flash slot. Same spirit, different mechanism. ↗
◇ Cheap-ESP audacity — smol's soul
  • ESP32 MARAUDERA WiFi/BLE multi-tool on a cheap ESP32 with a tiny touchscreen and a menu-driven handheld UI. smol borrows the form-factor genre — cheap ESP + tiny screen + menu navigation is exactly smol's physical shape and UX — plus a radio-manipulation kinship (both bend the 2.4 GHz radio to their will). Differs — smol is a cooperative mesh node, not a pentest tool, and it manipulates its own radio for ESP-NOW coexistence, not other people's networks. ↗
  • LEAFMINERA FOSS Bitcoin solo-miner for the ESP8266/ESP32 (NerdMiner-family, built on NerdSHA256plus) — openly a learning toy, since actually mining a block is astronomically unlikely. smol borrows the soul: a $5 chip doing something gloriously improbable for the joy and the learning of it — the same spirit as a shared-world snake MMO running on a clock. Differs — smol is a useful mesh (telemetry, time, display), not a lottery ticket. ↗
  • ATOMIC14Five single-button games (Breakout, Micro Racer, Defender, Jump Run, Heli Cave) built for this exact ESP32-C3 + 0.42″ OLED — and now flashed onto smol. The closest thing to a direct ancestor: living proof this precise board is a game console. Squarely in smol's play lineage. ↗
◇ Remote-management UX
  • PIKVMAn open-source IP-KVM on a Raspberry Pi — a pure-HTML5 web UI for remote keyboard/video/mouse, power control and BIOS access, with no client install. smol borrows the remote-management-appliance ethos and its clean web-control UX: manage the physical thing from anywhere, through a browser. Aspirational for smol's HA-side control surface — and delivered in #21, the node manager that sets any board's default screen from Home Assistant over retained MQTT, no reflash. Differs — PiKVM is a Linux Pi driving one other computer; smol is a fleet of bare-metal ESP32 mesh nodes managed via HA/MQTT + an OLED. ↗
◇ Lean real-time embedded
  • GRBLReal-time CNC motion-control firmware in tightly optimized C for an Arduino-class AVR — a G-code planner that looks 16 moves ahead, emits up to 30 kHz of jitter-free step pulses, and honors real-time override commands mid-stream. smol borrows the lean-real-time-firmware craft — deterministic behavior squeezed from a tiny MCU — and a loose design echo: GRBL interleaves out-of-band real-time commands with a streamed buffer, roughly the shape of smol draining ESP-NOW RX between MQTT poll cycles. Differs — GRBL is single-purpose motion with no radio or mesh; the echo is lineage, not a code steal. ↗

◇ BLE presence (the #22 basis) — smol's beacon-tracking idea would build on Bermuda (HACS trilateration that reuses existing bluetooth_proxy anchors) and ESPresense (dedicated MQTT anchors). Prior art and reference, not code smol borrows.
